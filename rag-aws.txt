Você é o Claude Code atuando em um repositório existente do SDK IU Lotus.

Contexto do projeto:
Estou desenvolvendo a fundação de RAG/base de conhecimento para um futuro agente de deploy de modelos da IU Lotus. O agente precisa consultar documentação relacionada a deploy, inferência, operação, troubleshooting, monitoramento, governança e sustentação.

Existem dois repositórios GitHub distintos de documentação. Cada um contém uma parte da documentação que deve alimentar o RAG. Ou seja, o repositório GitHub de documentação interna contém a documentação interna, o repositório GitHub de documentação pública contém a documentação pública, e a base de conhecimento final deve considerar o conteúdo combinado dos dois.

Repositórios de documentação que devem ser usados como fonte:

Documentação interna:
https://github.com/itau-corp-commons/itau-mr7-doc-documentacao-interna.git

Documentação pública:
https://github.com/itau-corp-commons/itau-rs7-doc-iulotus.git

A documentação da IU Lotus é atualizada constantemente nesses dois repositórios. Por isso, a base de conhecimento não deve ser tratada como estática. A solução precisa prever atualização recorrente da documentação no S3 e posterior ingestão/sync da Bedrock Knowledge Base.

Requisito de atualização:

* deve existir um caminho para atualização semanal da documentação, pois os repositórios podem mudar ao longo do tempo;
* também deve existir um caminho para atualização manual sob demanda, acionado pelo usuário quando houver correção importante, mudança crítica ou atualização urgente na documentação;
* a atualização manual deve permitir reenviar a documentação ao S3 e iniciar nova ingestão da Knowledge Base sem depender do ciclo semanal;
* não implemente GitHub Actions, pois não podemos alterar .github/workflows;
* a implementação deve deixar claro quais comandos/scripts permitem a atualização manual agora e quais partes poderiam depois ser executadas por um scheduler aprovado, como SageMaker, CodeBuild, EventBridge, pipeline interno, Jenkins, Airflow ou outro mecanismo validado pela squad.

Contexto da abordagem antiga:
Foi iniciada uma abordagem local dentro de:

agents/deploy_agent/

A abordagem antiga fazia:

* clone dos dois repositórios GitHub de documentação;
* leitura de arquivos .md, .mdx, .txt, .yaml, .yml e .json;
* chunking local;
* vetorização local com TF-IDF;
* persistência de índice local em data/rag_index;
* consulta local com scikit-learn/joblib;
* tentativa futura de automação por GitHub Actions.

Essa abordagem deve ser abandonada como caminho principal pelos seguintes motivos:

1. A automação por GitHub Actions dependeria de criar ou alterar .github/workflows na raiz do repo, e isso não é permitido ou ainda não foi aprovado.
2. TF-IDF é apenas lexical e teve qualidade limitada para o caso de uso.
3. Houve bloqueio de rede/proxy ao tentar usar embeddings do Hugging Face.
4. Não queremos manter índice vetorial local, vectors.joblib, vectorizer.joblib, chunks.jsonl e lógica própria de busca no repositório.
5. A squad aprovou migrar para uma abordagem AWS gerenciada com S3 + Amazon Bedrock Knowledge Base.

Objetivo novo:
Refatorar o código do agente para abandonar o RAG local com TF-IDF e preparar uma abordagem AWS.

A arquitetura alvo, em termos conceituais, é:

Repositório GitHub de documentação interna + Repositório GitHub de documentação pública
-> sincronização dos documentos
-> normalização dos arquivos relevantes
-> envio para S3
-> Amazon Bedrock Knowledge Base usando esse S3 como fonte de dados
-> ingestão/sync da Knowledge Base
-> agente consulta a Knowledge Base via boto3
-> Bedrock gera respostas com base nas fontes recuperadas

Mas a forma exata de implementar isso no repositório deve ser definida por você após análise do código existente. Use o padrão do projeto quando ele existir.

Tarefa 5: Sincronização dos documentos para S3
Implemente a sincronização dos dois repositórios GitHub de documentação para S3 da forma que achar mais adequada.

A sincronização deve ser pensada para dois modos de uso:

1. atualização manual sob demanda, para quando o usuário quiser refletir rapidamente uma correção ou alteração importante da documentação no RAG;
2. atualização recorrente semanal, para manter o S3 e a Knowledge Base alinhados com os repositórios de documentação que mudam constantemente.

O código não precisa implementar o agendamento semanal completo se isso depender de infraestrutura externa, mas deve ser estruturado de forma que o mesmo comando/script possa ser usado tanto manualmente quanto por um scheduler aprovado no futuro.

Requisitos funcionais:

1. Ler configuração de repositórios e AWS.
2. Clonar ou acessar os dois repositórios GitHub de documentação:

   * documentação interna: https://github.com/itau-corp-commons/itau-mr7-doc-documentacao-interna.git
   * documentação pública: https://github.com/itau-corp-commons/itau-rs7-doc-iulotus.git
3. Usar pasta temporária do sistema, nunca uma pasta temporária dentro do repo.
4. Capturar commit SHA de cada repo.
5. Filtrar arquivos relevantes.
6. Normalizar:

   * .md e .mdx como markdown;
   * .txt como texto simples;
   * .yaml/.yml como markdown com bloco yaml;
   * .json como markdown com bloco json.
7. Incluir metadados no documento normalizado, por exemplo:

   * repo;
   * tipo_documentacao, interna ou publica;
   * branch;
   * commit;
   * arquivo_original;
   * extensão_original;
   * data de ingestão.
8. Enviar os documentos normalizados para S3.
9. Preservar rastreabilidade do caminho relativo.
10. Gerar manifest JSON com:

* created_at;
* repos processados;
* tipo de documentação;
* commit por repo;
* arquivos enviados;
* sha256 de origem;
* s3_key;
* total de documentos.

11. Enviar manifest para S3.
12. Permitir limpar o prefixo antes de reenviar, se isso for útil.
13. Ter logs claros.
14. Tratar erros de forma explícita.

Não fazer chunking local como parte principal da solução. A fragmentação deve ficar preferencialmente sob responsabilidade da Bedrock Knowledge Base, salvo se você justificar tecnicamente outra decisão.

Tarefa 6: Ingestão da Knowledge Base
Implemente um script ou comando para iniciar a ingestão da Bedrock Knowledge Base.

A ingestão da Knowledge Base deve poder ser acionada após cada sincronização para S3, tanto no fluxo manual sob demanda quanto no fluxo recorrente semanal. O script/comando deve deixar claro que atualizar o S3 sozinho não basta: depois de enviar os documentos ao S3, é necessário iniciar a ingestão/sync da Bedrock Knowledge Base para que o RAG passe a considerar os novos conteúdos.

Requisitos:

1. Ler region, knowledge_base_id e data_source_id de config/env/args.
2. Usar boto3 client bedrock-agent.
3. Executar start_ingestion_job.
4. Imprimir ingestionJobId e status.
5. Não tentar criar a Knowledge Base via código, a menos que você explique claramente que isso é opcional e separado.
6. Não tentar criar OpenSearch Serverless via código.
7. Se ocorrer AccessDenied, mostrar mensagem clara.

Observação importante:
Ao tentar criar a Knowledge Base pela interface AWS, houve erro de IAM ao criar OpenSearch Serverless por falta de:

* aoss:CreateAccessPolicy
* aoss:CreateSecurityPolicy

Portanto, assuma que a Knowledge Base e o vector store serão criados pela interface AWS ou pelo time responsável. O código deve focar em sincronizar S3, iniciar ingestão e consultar.
